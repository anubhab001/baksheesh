# Baksheesh #
This [repository](https://github.com/anubhab001/baksheesh) contains source-codes related to Baksheesh ([IACR ePrint](https://eprint.iacr.org/2023/750)), a lightweight block cipher.

## Specification Notes ##
A few points are worth stating explicitly for an independent re-implementation.

* GIFT heritage and ZORRO heritage are two equivalent descriptions of the same cipher. For a given key and plaintext they produce identical ciphertext.
* The 128-bit state and key are indexed as `b_127 b_126 ... b_0`, where `b_0` is the least significant bit. The round key is added position-wise: `b_i` is XORed with `k_i` for every `i`.
* The key schedule is a one-bit cyclic right rotation of the 128-bit key, taken in the word-oriented layout used by the reference implementation. It is not a rotation of the plain hexadecimal string. The key nibbles are arranged into eight 16-bit words (most significant nibble first) and the bits of each word are read least-significant-first to form the 128-bit value that is rotated. The reference implementation `reference/baksheesh.py` and the accompanying test vectors are the authoritative definition.
* Equivalently, the key as written splits into eight words of four hexadecimal characters; the leftmost word is the least significant word of a 128-bit integer, this integer is rotated right by one bit, and the words are written back in the same order. Within every 16-bit word this agrees with the plain rotation of the hexadecimal string; the two differ only in the bit that wraps into each word. For example, the key `25798b6c2b24cd83281de76786213b86` has the next round key `12bc45b69592e6c1940ef3b343109dc3` (word-reversed value `3b868621e767281dcd832b248b6c2579`, rotated `9dc34310f3b3940ee6c1959245b612bc`, words restored).
* The plaintext and the key hexadecimal strings are read character by character, from left to right, into the 32 nibbles of the implementation arrays. The ciphertext hexadecimal string is the final state written in reversed nibble order. The test vectors follow the same convention.
* The input is thus read left to right and the output written right to left. This mixed ordering is kept so that the published test vectors stay valid.
* The test vectors bundled with the reference implementation are the authoritative set for implementation verification.
* A complete round-by-round encryption trace for one test vector is given in `reference/encryption_trace.txt`. It shows the input state, the round key and the output state of every round, with the intermediate values after each layer. It is generated by `reference/print_trace.py`. A compact per-round table of the same encryption, with both encodings of the plaintext and the ciphertext, is given in `reference/round_by_round.md`.
